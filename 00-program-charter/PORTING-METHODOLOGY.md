# SPP Porting Methodology

> **Purpose:** A step-by-step framework for porting any legacy shop-floor process into the new "Console-as-Brain" unified architecture.

This methodology guarantees that we never regress into building process-specific business logic in the execution layers (`shree_polymer_ops` or `legacy_bridge`).

---

## 1. Process Discovery & Payload Analysis
Before writing any code, understand how the process is currently mapped.
* **Inspect Legacy Execution:** Check the `Legacy Bridge` application (`sync_api.py`) and existing legacy Frappe apps to understand what documents the process currently creates (e.g., Stock Entry, Asset Movement).
* **Identify Data Sources:** Determine where the dynamic values (batches, expiry dates, operators) come from.

## 2. Console Template Creation (The Brain)
All routing, mapping, and logic must be configured here.
* **Create Process Template:** In `shree_polymer_console`, create the `Console Process Template` for the process.
* **Map the Sequence:** Define the exact `action sequence` the execution engines must run.
* **Resolve Variables:** Use Jinja-style placeholders (`{{batch_no}}`, `{{step_1.name}}`).
* **Handle All Business Rules:** If the process requires looking up a barcode to find an internal batch number, or generating a new serial number, **the Console must perform this lookup/generation before dispatching the payload**.

## 3. Ops Layer Execution (The Thin Client)
* **Zero Custom Logic:** The payload sent to Ops must be a "dumb" JSON object ready for execution.
* **Use Generic Handlers:** The Ops `TransactionEngine` will execute `create_doc`, `update_doc`, or `submit_doc` based on the sequence.
* **Strict Rule:** **NEVER** add `if process == "Deflashing"` or `_handle_deflashing_pre_save()` to `shree_polymer_ops/api.py`. If you find yourself writing process-specific python code in Ops, you have failed the architectural pattern. Move that logic back to the Console template or the Console's API payload builder.

## 4. Idempotency & Resiliency
* **Attach `reference_id`:** Every transaction must have a `reference_id` (typically a 13-digit Unix timestamp) generated by the frontend.
* **Idempotent Engines:** Both Ops and the Legacy Bridge must check `reference_id` before execution to prevent duplicate documents during offline-retry loops.

## 5. Audit & Validate
* **Simulate Dash Submission:** Submit a request from the Dash UI.
* **Check Logs:** Check `MES Transaction Log` on Ops and `Legacy Bridge Log` on Legacy. Both must show the exact same `reference_id`.
* **Verify Outputs:** Ensure the generated Frappe documents match the legacy system exactly.

## Summary Checklist for New Processes
- [ ] Console Process Template defined.
- [ ] All dynamic lookups/computations handled in `shree_polymer_console/api.py`.
- [ ] Payload contains `reference_id`.
- [ ] Ops `TransactionEngine` consumes payload using generic sequence actions.
- [ ] **NO** new process-specific code added to `shree_polymer_ops`.
