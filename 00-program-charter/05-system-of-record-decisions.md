# 05 — System-of-record decisions

This file answers: **at any given moment, which system owns the authoritative state for X?**

Multiple ERPs holding similar data raises legitimate questions about truth ownership. The porting program makes deliberate choices, captured here.

## Identity ownership

| Concept | System of record | Why |
|---|---|---|
| Submission `reference_id` | **Console** | Generated by Dash via `Date.now()`; unique on Console doctype; both ERPs reference it |
| Mix barcode (`C_YYMMDDXn`) | **Console** | Console authors it; Legacy honors via `bridge_mix_barcode`; Ops Stock Entry FG row uses it as `mix_barcode` and `batch_no` |
| Cut Bit batch (`Cutbit_<item_code>`) | **Console-coordinated** (output of Stage 5) | Console initiates; Bridge + Ops handlers materialize the legacy/native batches |
| Lot # (`LOT-YYYYMMDD-NNN`) | **Console** (Pattern A, target state) | Console-first generation per Wave 3 plan; both ERPs accept the value |
| Job Card name | **Legacy** | Legacy `create_planning_with_jobcards` generates; Console + Ops reference back |
| Production batch (`T-<lot>-<seq>`) | **Console MPE** | MPE on Console generates and propagates to both ERPs + Inspection Entries |
| Submitting user | **Console** (`submitted_by` field) | Console session user; mapped to ERPs as employee links |

## Inventory truth

Inventory is the trickiest case because **both Legacy and Ops independently maintain Stock Ledger Entries**. The architecture choice:

> **Neither ERP is the absolute truth for inventory; they must agree, and reconciliation is the verification mechanism.**

| Aspect | Detail |
|---|---|
| Both ERPs maintain Stock Ledger Entries | Yes — independent, parallel |
| Bridge writes are atomic per-ERP | Yes — each leg's SE submits independently |
| Single source of truth for "current inventory of item X in warehouse Y"? | **No** — both ERPs hold copies; agreement is checked at reconciliation |
| Console's `Console Stock Cache` | A **denormalised view** updated from Ops `impacted_balances` responses; not authoritative for accounting |
| If they disagree | An incident — manual investigation, NOT automated reconciliation |

### Why this design

- Real-time inventory consistency would require 2PC across ERPs (rejected per Principle 3)
- An "inventory broker" service would be a new single point of failure
- Both ERPs independently maintaining ledgers means either can serve as the operational source during the other's downtime
- Reconciliation (manual today, future automated) catches persistent drift

### Reconciliation cadence (current)

| Frequency | What's checked |
|---|---|
| Shift-end | Spot-check `Console Transaction Log` for `status != "Success"`; investigate Partials |
| Daily (manual) | Compare Stock Ledger summary on Legacy and Ops for the day; flag deltas > tolerance |
| Weekly | Compare item-level batch balances across both ERPs |
| Incident-driven | Any operator-reported inventory mismatch triggers ad-hoc reconciliation |

A **future epic** would automate reconciliation — out of program scope.

## Audit trail ownership

| Trail | System of record | Why |
|---|---|---|
| Console-side audit | **Console** (`Console <Process>.payload_snapshot` + `Console Transaction Log` rows) | Captures intent + per-leg status |
| Bridge-side audit | **Legacy** (`Legacy Bridge Log` rows) | Captures the Bridge's interpretation of payloads + traceback on failure |
| Ops-side audit | **Ops** (`Shree Polymer MES Log` rows) | Captures action execution + impacted balances |
| Cross-system event reconstruction | **All three logs together**, queryable by `reference_id` | No single system has the complete picture |

This is intentional. Each system's log captures **its own perspective**. The cross-reference key is `reference_id`.

## Configuration / master data ownership

| Master data | System of record | Notes |
|---|---|---|
| Items (Item Master) | **Legacy** | Synced to Console as `Console Item`; Ops uses native `Item` doctype synced from Legacy |
| BOMs | **Legacy** | Each ERP has its own BOM records; Bridge ensures alignment at submission time |
| Warehouses | **Each ERP independent** | Console `Console Warehouse` links to legacy + ops names via `Console Process Template.warehouses` rows |
| Workstations | **Legacy** | Console mirrors via `Console Workstation`; mapped to Ops native `Workstation` |
| Employees | **Legacy HR** | Console `Console Employee` mirrors; Console User has role assignments separately |
| Console Process Templates | **Console** | The canonical source of action sequences and routing rules |
| Legacy Sync Mapping | **Console** | Authoritative for how Console payloads map to Legacy doctypes |

## When does Legacy go read-only?

**Currently:** Not yet — Legacy receives submissions from the Bridge AND occasionally direct Desk submissions (for stages not yet ported).

**Target state (post-program):** Legacy custom doctypes for ported stages become read-only — populated only by the Bridge. Operators no longer submit directly to Legacy Desk for these stages.

**Trigger conditions for going read-only per stage:**

1. The stage has been fully ported AND deployed to production-staging
2. All operators have been trained on the Console Dash flow
3. At least one full month elapses with > 99% of submissions originating on Console
4. Production overseer signs off in writing

**What does NOT change when a stage goes read-only:**

- Legacy keeps generating Stock Ledger Entries (driven by the Bridge's submissions)
- Legacy reports keep working
- Historical legacy data remains queryable
- Out-of-program modules (Accounts, HR) continue normal operation

## Cross-ERP rename / refactor authority

| Operation | Who owns the decision |
|---|---|
| Adding a new item group | Legacy QA Lead (Items master is on Legacy) |
| Adding a new workstation | Shop Floor Supervisor + Legacy admin |
| Modifying a Console doctype field | **Production overseer** — coordinated change across Console + Bridge + Ops mapping |
| Modifying a legacy doctype schema | **Production overseer** — high blast radius (affects all reports) |
| Adding a new value-map entry on Bridge | Engineering Lead — must be tested before push |
| Adding a new ERPNext native doctype to Ops | **Production overseer** + Engineering Lead — needs Principle 2 compliance review |
| Deprecating a Console process | **Production overseer** + Shop Floor Supervisor |

## The "two batches for one event" problem

A successful Mixing submission creates a Batch on Legacy AND a Batch on Ops. Both have the same `batch_id` (the Console-generated `mix_barcode`). Are they the same Batch?

**Architectural answer:** They are **two database rows** representing the **same physical lot**. The shared `batch_id` (which equals the Console mix barcode) is the cross-ERP link.

**Implications:**

- Reports asking "show me Batch X" must specify the ERP. There's no global Batch view in this architecture (unless built later as a separate epic).
- Stock Ledger movements for "Batch X" happen on both ERPs independently and should agree (reconciliation).
- Item-level batch quantity queries (Frappe's `get_batch_qty`) return the ERP-local value; the **true** quantity is the agreed-upon value.

This is the cost of dual-ERP architecture. The benefit (resilience + reporting flexibility) is judged worth it.

## Operator session ownership

| Aspect | Where it lives |
|---|---|
| Operator login | Console (Frappe session) |
| Active role | Console `Console User.roles` |
| Cross-ERP authentication | Console's `oauth_client` builds headers; per-user tokens for Ops; API key signature for Bridge |
| Session timeout | Console-managed (Frappe default) |

The operator NEVER logs into Legacy or Ops directly during normal operation. Console mediates all access.
