# 03 — Functional requirements

Each requirement is **numbered**, **individually testable**, and **traced to specs** in `08-traceability.md`. Variant-specific requirements are tagged `[MBM-only]` or `[FBM-only]`; everything else applies to both.

## FR-MIX — Submission flow

### FR-MIX-001 — Single-operator submission
A Mixing Operator must be able to record a mixing event by:
1. Scanning their employee badge (validates role membership in `Mixing Operator`)
2. Selecting the produced item from a Console-filtered dropdown
3. Scanning each raw material barcode (auto-fills item / batch / qty / warehouse)
4. Entering the produced quantity in kilograms
5. Pressing Submit

The submission must complete and surface success/failure feedback within **30 seconds** under normal load.

### FR-MIX-002 — Parallel multi-system sync
A successful submission must produce equivalent records on BOTH:
- **Legacy** ERPNext: a `Delivery Challan Receipt` with `inward_material_type` = `"Master Batch"` [MBM] or `"Compound"` [FBM], a child `dc_items` row per consumed raw material, plus an auto-created Manufacturing Stock Entry
- **Ops** ERPNext: a `Stock Entry` (purpose: Manufacture) with consumption rows for raw materials and an FG row for the produced compound

Both records must use the same Console-generated identifiers (see FR-MIX-005).

### FR-MIX-003 — Partial sync recovery
If only one of the two ERPs accepts the submission successfully:
- The Console record must reflect `sync_status = "Partial"`
- The failed leg's error must be captured and surfaced to the operator
- The operator must have a retry path that does NOT create duplicate records on the successful leg
- The retry path must be available from both the Dash success modal AND the `Console Transaction Log` list view

### FR-MIX-004 — Audit trail invariant
Every submission attempt — including those with incomplete or invalid payloads — must leave a record on Console for diagnostic purposes. The record may be in a "Pending" state pending validation; the `payload_snapshot` field must contain the full submitted payload as JSON for replay.

Even when strict validation would reject the submission (e.g. zero qty), the audit-trail write path must succeed and store the record. Only the Desk UI direct-insert path runs strict validation.

### FR-MIX-005 — Console-authoritative barcode
The mix barcode (format: `C_YYMMDDXn`) must be generated by Console and recognised as the **single source of truth** across all three systems:
- Console: stored on the Mixing record's `mix_barcode` field
- Legacy: stored on the DCR's `bridge_mix_barcode` field; legacy MUST NOT generate its own barcode when Console provides one
- Ops: stored on the FG row of the produced Stock Entry as `mix_barcode` and `batch_no`

Downstream processes (Compound Inspection, Sheeting, Final Batch Mixing) must be able to scan this barcode and resolve it to the source Mixing record on any of the three systems.

### FR-MIX-006 — Reference ID round-trip
Console must generate a unique `reference_id` (13-digit milliseconds timestamp) per submission. This ID must:
- Be unique on the Console Mixing doctype (database constraint)
- Round-trip to Legacy as the DCR's `dc_no` field
- Round-trip to Ops as the MES Log's `reference_id` field
- Be respected as the idempotency key on retry (Bridge + Ops both deduplicate by this key)

## FR-MIX — Operator UX

### FR-MIX-010 — Role-based item filtering
The produced item dropdown must filter to items in the allowed item group, as configured per process on `Console Process Template`:
- `[MBM-only]` items in item group **Master Batch**
- `[FBM-only]` items in item group **Compound**

The operator must not see items from other groups, even if they have read permission elsewhere.

### FR-MIX-011 — Role-based operator filtering
The operator dropdown must filter to employees holding the role required by the process template (default: `Mixing Operator`). Operators without this role must not appear in the list.

### FR-MIX-012 — Backdating restrictions
- Regular Mixing Operators: `posting_date` is clamped to "today or yesterday" — earlier dates are rejected
- System Manager / Administrator role: may set `posting_date` to any past or current date
- Forward-dating (future `posting_date`) is rejected for all roles

### FR-MIX-013 — Real-time barcode validation
Each raw material barcode scan must be validated against current stock before being added to the consumption list:
- Barcode must resolve to an active batch in a source warehouse
- The barcode's item must be a permitted input (per BOM if BOM-driven; otherwise per Console Process Template)
- Available qty must be greater than zero

Validation failures must surface inline in the BOM panel; the row must not be added to the submission.

### FR-MIX-014 — Live Feedback per-target status
After submit, the operator must see a status panel with one row per target ERP. Each row must independently transition through:
1. `Pending` (Console initialized the leg)
2. `Processing` (HTTP request in flight)
3. `Success` or `Failed` (final state)

The status must be visible within 1 second of each transition. Status must persist on the screen until the operator dismisses or starts a new submission.

### FR-MIX-015 — Printable barcode label
On successful submission, the produced mix barcode must be rendered as a printable label (e.g. 75mm × 75mm thermal label) ready for one-click printing.

## FR-MIX — Variant-specific behaviour

### FR-MIX-020 [MBM-only] — Raw materials only
A Master Batch Mixing submission must accept only raw material rows in `consumption_items`. Rows must not include any item from the Master Batch or Compound item groups (other than as the produced item).

### FR-MIX-021 [FBM-only] — Master Batch consumption
A Final Batch Mixing submission must:
- Include exactly ONE row in `consumption_items` with `is_batch_item = 1`, representing the consumed Master Batch lot
- Include one or more raw material rows with `is_batch_item = 0`
- The MB row's `mix_barcode` must match an existing, in-stock Master Batch lot on both Legacy and Ops

### FR-MIX-022 [FBM-only] — MB lot stock availability check
Before the operator can submit, the system must verify the scanned Master Batch lot has sufficient available stock for the FBM submission. The check must be enforced on Ops at submit time (legacy may rely on its own stock validation).

### FR-MIX-023 [FBM-only] — Cut-bit recycling input
Final Batch Mixing must accept **cut-bit batches** (produced by upstream Sheeting Process) as raw material inputs. Cut-bit batches are identified by the `Cutbit_` prefix on the batch number. When consumed, they must reduce the Console + Legacy + Ops cut-bit inventory equivalently.

## FR-MIX — Data quality

### FR-MIX-030 — Mandatory fields on strict path
When a submission reaches the Desk UI direct-insert path (not via the Dash audit-trail bypass), the following fields must be mandatory:
- `item_code`
- `qty` > 0
- At least one row in `consumption_items` (with item_code and qty > 0)

### FR-MIX-031 — Soft mass-balance signal (recommended, currently NOT enforced)
The system **should** warn the operator if the total consumption qty differs from the produced qty by more than 5%. The warning must NOT block submission — it logs a structured note and surfaces in the success modal.

**Current implementation status:** NOT IMPLEMENTED. Documented as a deferred decision in spec `10-risks-and-decisions.md`. Business has chosen to capture deviations rather than block on them.

### FR-MIX-032 — Cross-system identity consistency
For any successful submission, the following must be true at steady state (within 60 seconds of submit):
- Console `Console Master Batch Mixing` / `Console Final Batch Mixing` has `sync_status = "Success"` and `docstatus = 1`
- Legacy `Delivery Challan Receipt` exists with `dc_no = reference_id`, `bridge_mix_barcode = <Console mix_barcode>`, and a child `dc_items` row count equal to the Console payload's consumption item count
- Ops `Stock Entry` exists with consumption rows in the source warehouse matching the Console rows by `item_code` + `qty`, plus one FG row in the target warehouse with `mix_barcode = <Console mix_barcode>`

## FR-MIX — Retry, idempotency, recovery

### FR-MIX-040 — Idempotent submission
If the operator (or Dash retry) submits a payload with a `reference_id` that already exists on Console as a successful submission:
- Console must reject the second submission cleanly (DuplicateEntryError surfaced as a clear error to the operator)
- No new records may be created on Legacy or Ops

### FR-MIX-041 — Idempotent leg retry
If the operator retries a failed leg (`Console Transaction Log` row in `Failed` status):
- The retry must reuse the same `reference_id`
- Legacy/Ops must deduplicate by `reference_id` and return success without creating a duplicate document
- On the second success, Console's `apply_bridge_result` callback must promote `sync_status` from `Partial` to `Success` and auto-submit the Console doc

### FR-MIX-042 — Concurrent callback safety
When both Legacy and Ops callbacks land near-simultaneously (within milliseconds of each other), the final state of the Console record must be deterministic and correct: `sync_status = "Success"` and `docstatus = 1`, regardless of which callback arrives first.

This is the **load-bearing race-safety requirement** that drove the 5-step `apply_bridge_result` pattern. Any future change to the callback handling must preserve this invariant.

## FR-MIX — Logging and observability

### FR-MIX-050 — Per-leg transaction log
Every submission must produce one `Console Transaction Log` row per target ERP. Each row must record:
- The target ERP (`Legacy` or `Ops`)
- The request payload sent
- The response received (including remote document name on success, traceback on failure)
- The final status (`Success` / `Failed` / `Partial`)
- Timing metadata (creation time, completion time)

### FR-MIX-051 — Error visibility to operator
On any leg failure, the operator must see:
- Which leg failed (Legacy or Ops)
- A first-line error summary (no full traceback in the Dash UI)
- A "Retry" button that does not require re-entering any data

### FR-MIX-052 — Error visibility to overseer
The production overseer must be able to query, from `Console Transaction Log`, all submissions in the last N hours that ended in `Partial` or `Failed`, with sufficient detail to either trigger a retry or escalate to engineering.
