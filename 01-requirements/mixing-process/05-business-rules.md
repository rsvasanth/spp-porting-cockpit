# 05 — Business rules

These are the constraints, invariants, and "why" decisions that drive the specifications. Each rule explains the **business reasoning** behind an implementation choice. Specs document the HOW; this file documents the WHY.

## BR-MIX-001 — Operation-to-material-type derivation

**Rule:** The legacy DCR's `inward_material_type` field must be derived from the Console payload's `config.operation`:

| `config.operation` | `inward_material_type` |
|---|---|
| `"Master Batch Mixing"` | `"Master Batch"` |
| `"Final Batch Mixing"` | `"Compound"` |
| (anything else) | `"Compound"` (default) |

**Why:** Legacy DCR branches on `inward_material_type` to take the right sub-path on submit. Master Batch path runs `create_master_batch_stock` + helpers; Compound path runs `validate_final_batches` + `create_wo_final_batch_mixing` + `make_stock_entry_final_batch`. Getting this wrong corrupts the entire downstream chain.

**Risk:** The default `"Compound"` silently masks unmatched operations. Any new operation type must explicitly extend the value-map. Monitoring on the default's frequency would catch silent bugs.

## BR-MIX-002 — Mass balance NOT enforced

**Rule:** The system MUST NOT block a Mixing submission when total consumption differs from produced qty by any amount.

**Why:** Mass deviations are a real production signal. A 5% drift may indicate:
- Operator measurement error (correctable downstream)
- Loss to mixer cleaning (expected; should be captured)
- Mis-scanned consumption row (should surface in QA, not at mix time)

Blocking at submit time would either:
- Force the operator to falsify the entry to pass validation, OR
- Block legitimate production while the issue is investigated

**Decision history:** The plan doc `01_WAVE1.md` called for a 0.5% mass balance check. The shipped implementation deliberately omits it. Production overseer accepted this trade-off; downstream Compound Inspection's deviation flow is the formal correction channel.

**Future consideration:** A soft-warning version (5% tolerance, logs but doesn't block) may be reinstated. Tracked in spec `10-risks-and-decisions.md`.

## BR-MIX-003 — DCR is the legacy target (not a new doctype)

**Rule:** Mixing submissions land on legacy as `Delivery Challan Receipt` with discriminating `inward_material_type`, NOT as a new dedicated legacy doctype.

**Why:**
- Downstream legacy reports (operational, QA, audit) already query DCR.
- Operations staff are trained on DCR workflow.
- A new doctype would require coordinated retraining + report re-pointing across multiple sites.
- The reuse pattern survives because `inward_material_type` is a clean discriminator.

**Implication:** Any schema change to legacy DCR affects all inbound material flows (Mixing, Compound Inspection's legacy SE, etc.), not just Mixing. Schema changes must be coordinated.

## BR-MIX-004 — Parallel sync, not two-phase commit

**Rule:** Legacy and Ops submissions run independently in parallel. There is NO transactional rollback across the two ERPs.

**Why:**
- Sequential sync would double submission latency.
- Either ERP can be taken offline without blocking the other.
- Failure recovery via operator retry is simpler than compensating transactions across two systems.
- The eventual-consistency window (seconds during outages) is acceptable to the business.

**Cost:** A `Partial` sync state exists. The business accepts this and uses the `Console Transaction Log` for visibility.

## BR-MIX-005 — Console as the single barcode authority

**Rule:** Console generates the mix barcode (format `C_YYMMDDXn`) and BOTH ERPs honor it. Legacy must NOT generate its own barcode when Console provides one (via `bridge_mix_barcode`).

**Why:**
- Pre-Console era: each ERP generated its own barcode independently. Cross-system traceability required maintained translation tables — fragile.
- Console as single authority eliminates the translation problem. The same barcode appears on Legacy DCR, Legacy SE, Ops SE, downstream Compound Inspection, all subsequent processes.
- The `C_` prefix is a deliberate signal: it indicates "Console-generated, do not regenerate."

**Risk:** If `bridge_mix_barcode` is missing from a payload, legacy may fall back to its own generator. This would create cross-system drift. Bridge tests verify the field round-trips.

## BR-MIX-006 — Reference ID as cross-system idempotency key

**Rule:** The 13-digit millisecond timestamp `reference_id` (generated by Dash via `Date.now()`) is the cross-system idempotency key. Console doctype enforces uniqueness; Bridge respects it; Ops MES Log respects it.

**Why:**
- A globally unique key enables idempotent retry. The Bridge can safely deduplicate without per-process logic. Ops can safely deduplicate the same way.
- Millisecond precision is enough; collision probability across multiple operators in a single ms is negligible.
- Using a timestamp (not a UUID) makes the ID human-readable for ops triage.

**Implication:** Re-using a `reference_id` is forbidden. Any system that drops the constraint compromises retry safety.

## BR-MIX-007 — `is_batch_item` flag distinguishes MB consumption in FBM

**Rule:** [FBM-only] The Final Batch Mixing payload must mark the consumed Master Batch row with `is_batch_item = 1`. All other consumption rows have `is_batch_item = 0`.

**Why:**
- Legacy DCR's `validate_final_batches` branches on this flag to take the **batched FB path** (which creates two stock entries: one for MB consumption, one for Compound production) versus the **non-batched path** (single SE).
- Without this flag, FBM would run the wrong sub-path, producing incorrect inventory moves.

**Risk:** If the Dash forgets to set this flag for the MB row, legacy silently takes the non-batched path. Mitigation: Bridge's `populate_compound_deviation_fields`-style backfill could detect MB consumption from item group; currently not implemented for FBM.

## BR-MIX-008 — Operator must hold Mixing Operator role

**Rule:** Submitting a Mixing record requires the submitting Console User to have the `Mixing Operator` role (or higher: System Manager / Administrator).

**Why:**
- Audit accountability — every submission must be traceable to an authorized operator.
- Training compliance — only trained operators should run mixing equipment.
- Permissions hygiene — production data must not be writable by unrelated roles.

**Implementation note:** Role checked at three layers: (1) Frappe doctype permissions, (2) Dash UI button gating, (3) server-side `get_available_employees` filter.

## BR-MIX-009 — Backdating limited to admin roles

**Rule:** Only System Manager / Administrator roles may set a `posting_date` more than 24 hours in the past. Mixing Operators may only post for "today or yesterday."

**Why:**
- Late entry corrections happen (operator forgot to log a mix during a busy shift). Limiting to "yesterday" supports the common case.
- Arbitrary backdating could be abused to falsify production records. Admin roles are accountable for such corrections.
- Forward-dating is forbidden for all roles.

## BR-MIX-010 — Cut-bit recycling is a valid FBM input

**Rule:** [FBM-only] Final Batch Mixing must accept cut-bit batches (produced by upstream Sheeting) as raw material inputs. Cut-bit batches are identified by the `Cutbit_` prefix in the batch number.

**Why:**
- Sheeting produces edge waste that's still usable compound; recycling it back into FBM is a sustainability + cost benefit.
- The `Cutbit_` prefix is the cross-system convention that distinguishes recycled material from fresh raw materials.
- Downstream stock ledger reconciliation depends on cut-bit consumption appearing on both Legacy and Ops.

**Implication:** Changes to the `Cutbit_` prefix convention (across Sheeting, Cut Bit Transfer, FBM) must be coordinated.

## BR-MIX-011 — Audit-trail bypass for partial payloads

**Rule:** The Console backend `_safe_local_create` must accept and persist a Mixing record even when the payload is incomplete (missing fields, zero qty, empty consumption_items). Strict validation is bypassed via `flags.from_local_cache = True`.

**Why:**
- A failed submission is operationally relevant — the operator did something, even if the data is malformed.
- Silently dropping bad submissions hides bugs (in Dash, in scanner config, in operator workflow).
- The full payload is preserved in `payload_snapshot` for replay/diagnostic.

**Implication:** Existence of a Console Mixing row does NOT mean the submission was valid. Use `sync_status = "Success"` as the truth test, not row existence.

## BR-MIX-012 — Auto-submit only on full success

**Rule:** A Console Mixing record's `docstatus` transitions from 0 (Draft) → 1 (Submitted) only when `sync_status = "Success"` (both legs Synced).

**Why:**
- A Draft record means "Console has a pending submission." Operations can see it's not done.
- A Submitted record means "both ERPs have it." Downstream processes can safely consume.
- Auto-submitting on `Partial` would falsely signal completion.

**Implementation:** The 5-step `apply_bridge_result` pattern's step 5 fetches a fresh doc and submits only if `sync_status = "Success" AND docstatus = 0`.

## BR-MIX-013 — Bridge SE lookup must support 6 strategies

**Rule:** Downstream Compound Inspection requires `stock_id` to be set on the legacy CI, pointing to the Mixing's manufacturing SE. The Bridge's `_lookup_legacy_stock_entry` must try 6 resolution strategies in priority order.

**Why:**
Each strategy covers a real production case:
1. `mix_barcode == spp_batch_no` — most common
2. `spp_batch_number` stripped of `C_` prefix — handles legacy without prefix
3. Direct `spp_batch_number` match — direct match case
4. `mix_barcode` vs payload — when they differ
5. Compound format `{item_code}_{spp_batch_no}` — Sheeting synthesis
6. `batch_no` fallback — last-ditch

Removing a strategy breaks the cases it covers. New strategies should be appended at the end, not inserted at higher priority.

## BR-MIX-014 — Race-safe callback aggregation

**Rule:** When Ops and Legacy callbacks land near-simultaneously on the Console doctype's `apply_bridge_result` method, the final `sync_status` must reflect the actual DB state — not stale in-memory state.

**Why:**
The Compound Deviation saga (2026-04-29 → 2026-05-01) demonstrated that:
- Two callbacks running concurrently both read `self` (stale)
- Both compute aggregate based on their own stale view
- The slower callback's write can regress an earlier `Success` to `Partial`

The 5-step pattern enforces:
1. Atomic per-field write for the current leg only
2. Re-read both legs from DB (atomic snapshot)
3. Aggregate from DB state
4. Self-heal — if both legs Synced but aggregate is wrong, correct it
5. Auto-submit only after fetching a fresh doc instance

**Any future change to callback handling must preserve this race-safety contract.**
